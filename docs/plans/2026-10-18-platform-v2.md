# Manang Platform v2: Plan

Status: proposed, 2026-10-18. Supersedes the shell and plugin sections of
`2026-10-13-manang-architecture-design.md`. Decisions below marked **(decided)**
were confirmed by the product owner on 2026-10-18; everything else needs review.

## 1. Why a second plan

A review of the running app showed that the backend is strong but the product is
not yet what was intended:

1. **No home.** Once a project is open there is no way to see or switch projects.
   An Overleaf-style home (projects, recent, templates, settings) is missing, and
   the editor sidebar and the home are different surfaces with different jobs.
2. **Settings has no UI.** The settings plugin exists; nothing renders it.
3. **The figure editor is not a whiteboard.** It lacks what people expect from
   a normal whiteboard tool: real selection and transform handles, snapping,
   grouping, connectors, layers, rich text, clipboard, and a fluid canvas.
4. **Plugins are headless.** Our plugins are command handlers behind a fixed UI.
   The original vision was: *a user builds a plugin (for example `.docx` support)
   and the app just works with it.* That needs plugins to contribute document
   types, editors, views and importers/exporters, not only commands.
5. **No scope distinction.** Some plugins extend the whole app (git, search,
   settings, themes); others exist only for a kind of document (Typst, LaTeX,
   figure, docx). The system must say which is which.

## 2. Principles

* **Everything is a plugin, including first-party features.** The shell is a host
  that renders what plugins contribute. If a first-party feature needs a
  privilege a third-party plugin cannot have, the platform is wrong.
* **Dogfood the extension points.** The figure editor and the docx editor are
  built as plugins through the same public mechanism.
* **Logic in WASM/native, UI in a sandbox.** Plugin logic stays behind the
  Wasmtime component boundary (ADR 0003). Plugin UI runs in an isolated webview.
  The bridge between them is the kernel's capability-checked command channel.
* **Brand stays.** Dark base, Acid lime accent, radius 0, DM Sans/Mono. Plugin UI
  receives the design tokens and a small stylesheet so it looks native.

## 3. Plugin model v2

### 3.1 Two scopes **(decided)**

| Scope | Activates | Examples |
| :--- | :--- | :--- |
| `system` | At app start (or on demand) | settings, git, search, themes, citations, spellcheck, plugin manager |
| `document` | When a document of a type it declares is open | Typst, LaTeX, Markdown, figure, docx |

A document plugin is loaded lazily and unloaded when its last document closes.
Per-project enable/disable is supported for both scopes.

### 3.2 Contribution points

A plugin declares what it adds in `manifest.toml`. The kernel keeps one registry
per contribution point; the shell renders from the registry and never from a
hard-coded list.

```toml
[plugin]
name = "docx"
version = "0.1.0"
scope = "document"          # system | document
tier = "wasm"               # native | wasm  (logic)

[[contributes.document-types]]
id = "docx"
title = "Word document"
extensions = ["docx"]
open-with = "default"       # default | optional
editor = "ui/editor.html"   # sandboxed webview entry (optional)
preview = "ui/preview.html" # optional
new-file = { title = "Word document", template = "templates/blank.docx" }

[[contributes.importers]]   # other formats into this type
[[contributes.exporters]]   # this type to PDF, HTML, ...
[[contributes.views]]       # sidebar panel / bottom panel tab / status item / toolbar
[[contributes.commands]]
[[contributes.settings]]
[[contributes.keybindings]]
[[contributes.themes]]
```

New in the kernel (today it only has commands and four hooks):
document-type registry, view registry, importer/exporter registry, activation
events, scope-aware lifecycle, and manifest `namespaces` (the settings plugin
needed a three-manifest workaround because command ids must start with the
plugin name).

### 3.3 Document sessions

Modelled on VS Code's custom editors, which split a *view* (a webview) from a
*document model* with load, save, backup, revert and undo.

* Text types use the first-party editor plugin's rope-backed session.
* Structured or binary types (docx, figure) provide their own session: the
  plugin's logic component implements `open(bytes) -> model`,
  `apply(edit)`, `save() -> bytes`, `backup()`, `undo/redo`. The shell owns tabs,
  dirty state, save, hot exit and "open with".
* File association resolution: extension -> document type -> preferred plugin;
  the user can pick another via "Open with".

### 3.4 Plugin UI: sandboxed webview **(decided)**

* Each UI entry is served from a custom protocol with an unguessable per-plugin
  token (`manang-plugin://<token>/ui/editor.html`) and loaded in a sandboxed
  frame (`sandbox="allow-scripts"`, opaque origin) under a strict CSP: no
  network, no `eval`, no navigation.
* The only way out is a versioned `postMessage` bridge. The host validates every
  message in Rust against the plugin's manifest permissions; a plugin can only
  call its own commands and services it was granted.
* A small JS SDK (`@manang/plugin-ui`) wraps the bridge: `commands.invoke`,
  `document.*` (the session), `settings.*`, `theme` tokens, `ui.notify`,
  `clipboard`.
* **Security spike first.** Research found no official Tauri guidance for plugin
  UI, an advisory that iframes can reach Tauri APIs, and an open issue about
  opaque-origin isolation frames on Windows. Phase 0 must prove that a sandboxed
  plugin frame cannot call Tauri IPC on Linux, macOS and Windows. If it cannot be
  proven, plugin UI moves to a separate webview per plugin with its own (empty)
  capability set.

### 3.5 Distribution

Plugin = a folder or `.manangplugin` archive: `manifest.toml`, `plugin.wasm`,
`ui/`, assets. Install from file, URL or (later) a curated registry. The plugin
manager shows scope, permissions, version and logs, and asks consent for
permissions at install. Signing is a documented follow-up.

## 4. Application structure

Two top-level surfaces, one window.

### 4.1 Home (Overleaf-style)

```
┌────────────┬───────────────────────────────────────────────────────┐
│ Manang     │  Projects                [Search…]   [New] [Open] [Import]
│            ├───────────────────────────────────────────────────────┤
│ Projects   │  ┌───────┐ ┌───────┐ ┌───────┐   Filters: Typst LaTeX │
│ Recent     │  │ thumb │ │ thumb │ │ thumb │   Sort: modified        │
│ Templates  │  │ name  │ │ name  │ │ name  │   Grid / List           │
│ Plugins    │  │ date  │ │ date  │ │ date  │                         │
│ Archive    │  └───────┘ └───────┘ └───────┘                         │
│ ────────   │                                                       │
│ Settings   │                                                       │
└────────────┴───────────────────────────────────────────────────────┘
```

* Project cards: first-page thumbnail, engine, last modified, git state, tags.
* Actions: open, rename, duplicate, archive, delete to trash, reveal in file
  manager. Search and filter across projects. Pinned projects.
* New project: blank per engine, journal templates (IEEE, ACM, Nature, arXiv),
  or from a document type a plugin contributes. Import: folder, zip, git clone.
* Needs a project registry (new, in the project plugin): known projects with
  metadata, independent of "recent".

### 4.2 Workspace (the editor)

The workbench already built (activity bar, side panels, tabs, preview, Problems,
status bar) with these changes:

* Renders **only from contribution points**: panels, status items and toolbar
  entries come from plugins; first-party ones are not special.
* A **Home** button and a project switcher (Ctrl+O) return to Home or switch
  project without closing the app. Later: multiple windows.
* Tabs host any document type, so a figure or a `.docx` opens as a tab with its
  plugin's editor.

### 4.3 Settings

A full page (not a drawer), generated from `settings.schema`, so plugin settings
appear automatically.

* Categories: General, Editor, Appearance, Compile, Files, Keybindings, Plugins,
  Network and privacy, About. Search across all settings.
* User and project scope switch; changed-from-default marker; reset per setting.
* Keybinding editor with conflict display; theme picker.
* Plugin settings grouped under each plugin.

## 5. Figure system: whiteboard grade **(decided)**

Requirements, in priority order:

1. Infinite canvas, smooth pan and zoom, minimap, touch and pen support.
2. Selection: click, shift-click, marquee, select-all, lock, transform handles
   (resize, rotate, aspect lock), nudge with arrow keys.
3. Snapping and smart guides, grid, align and distribute, equal spacing.
4. Shapes: rectangle, ellipse, polygon, line, arrow, freehand ink with pressure
   (perfect-freehand), highlighter, eraser; text boxes and sticky notes; images.
5. **Connectors** bound to shapes that follow them when moved.
6. Grouping, frames, layers and z-order, duplicate, copy and paste (including
   between figures and from the system clipboard).
7. Style panel (stroke, fill, opacity, dash, arrowheads, font); style presets.
8. **Math labels** rendered through the Typst plugin; stencil libraries for
   physics, circuits, graphs, commutative diagrams.
9. Undo/redo with grouped transactions; autosave; export SVG, PNG, PDF; embed in
   Typst, LaTeX and Markdown via the saved `.svg` next to the `.figure.json`.
10. Later: real-time collaboration (CRDT).

Approach: a **decision gate** in Phase 0. Compare an MIT whiteboard engine
(Quickdraw looks like the closest candidate: MIT, zero dependencies, vanilla JS;
the claims come from its own site and its license, watermark behaviour and
quality must be verified; AGENTS.md forbids watermarks and licensed SDKs)
against an in-house engine, using the list above as the rubric. Persistence and
export stay in Rust (`manang-figure`, deterministic SVG). The interactive layer
is the figure document plugin's webview, so it also proves the plugin UI model.

## 6. The `.docx` plugin **(decided: full editor and preview)**

This is the acceptance test of the whole platform: built only through public
extension points, as a third party would.

* Document type `docx`; webview editor with page view, preview, and export to
  PDF; converter logic in a WASM component (parse and serialise OOXML,
  preserving parts it does not understand so a round trip does not destroy
  content).
* Research: no MIT, headless, paginated `.docx` editor exists. Tiptap's DOCX
  and pagination are paid. SuperDoc (ProseMirror-based, pre-1.0) is a candidate
  whose license and fidelity must be verified. A ProseMirror core with our own
  pagination and OOXML mapping is the fallback. Word fidelity is a deep problem:
  v1 targets the common subset (headings, paragraphs, character styles, lists,
  tables, images, page setup, headers and footers) and says so plainly.

## 7. Phases

| Phase | Goal | Deliverables |
| :--- | :--- | :--- |
| **0. Spikes (1 week)** | Remove the three big unknowns | (a) plugin-UI security spike on 3 OSes; (b) whiteboard engine evaluation against the rubric; (c) docx stack evaluation. One ADR each. |
| **1. Platform v2** | Plugins can contribute UI and documents | contribution registries, scopes and activation, document sessions, webview host and bridge, `@manang/plugin-ui` SDK and UI kit, manifest v2; migrate first-party plugins; plugin docs. |
| **2. Product shell** | The app a normal user expects | Home and project registry, workspace driven by contributions, Settings page, Plugin manager, project switcher. |
| **3. Figure editor** | Whiteboard-grade drawing | figure document plugin per section 5. |
| **4. docx plugin** | Prove the vision | per section 6. |
| **5. Production** | Shippable | packaging and sidecars (LaTeX worker), signing, auto-update, CI gates, performance budgets, security review, accessibility audit, crash reporting opt-in. |

In flight and to land first: the Writing tools plugin; wiring Markdown and
Citations into the shell; pointing the Search and Git panels at their real
commands; full-workspace test run.

## 8. Risks and open questions

* **Plugin UI isolation** (section 3.4): the main security risk; gated by the
  Phase 0 spike.
* **Whiteboard quality**: a polished canvas is months of detail work; the
  evaluate-then-adopt-or-build gate keeps that visible.
* **docx fidelity**: scope v1 explicitly; expect limits.
* **Performance budgets** (AGENTS.md §4.2) must hold with plugin webviews and
  multiple documents; measure in Phase 1, not Phase 5.
* **Registry and trust model** for third-party plugins (signing, review) is not
  designed yet.
* **Settings and keybinding ids** proposed by the settings plugin need to be
  reconciled with the shell's commands.
