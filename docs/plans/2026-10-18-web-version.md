## 1. Goal, scope, and the honest summary

**Goal.** Let a stranger open a URL and write a Typst or Markdown document with
Manang's editor, preview, search, figures and (optionally) the AI agent and a
live session, with nothing installed. Later: accounts, optional end-to-end
encrypted cloud sync, live collaboration across devices.

**Honest summary.**

1. The Rust core largely can run in the browser, and the architecture already
   points that way (AGENTS.md invariant 5, the sans-IO `manang-live` core, the
   `Kernel` client in the frontend). But the audit is not done: several crates
   today pull OS-only code (`manang-project`: `gix`, `notify`, `ignore`;
   `manang-citations`: `ureq`; `manang-typst`: `rayon`). A first task is a
   `wasm32-unknown-unknown` audit (section 3.1).
2. Typst is the best first citizen on the web (pure Rust, the Typst web app
   proves the engine runs in a browser **[K]**). LaTeX is not: the only route
   that fits our model is the Tectonic WASI module in a Worker with a bundle
   served over HTTPS (research W8, 2 to 3 weeks, XeTeX only, speed unknown).
   First web release: **Typst and Markdown; LaTeX is "desktop only" with a
   clear message**, then a LaTeX beta behind a flag.
3. The server side is small if we keep the design discipline: the server never
   sees document plaintext, never runs a CRDT, never renders. It authenticates,
   stores ciphertext, and forwards frames. That keeps the Rust Worker tiny and
   the privacy claim simple.
4. Infrastructure cost is not the problem. At 10,000 monthly active users it is
   in the tens of dollars a month (section 8.4). The real costs are abuse,
   support, the security review of auth and the key-recovery story.
5. The riskiest unknowns are technical and cheap to test: does the core compile
   to wasm and meet the latency budget (Typst recompile in a single browser
   thread), and does the WebAuthn PRF extension work widely enough to wrap
   keys. Both are Phase 0 spikes of a few days.

## 2. Hosting facts that shape the design

All **[V]** on 2026-10-18 unless marked.

* **Pages vs Workers static assets.** Cloudflare's migration guide says "what
  works in Pages works in Workers" unless stated, and that Workers has "a
  distinctly broader set of features". Pages-only: custom domains whose
  nameservers are not on Cloudflare, plus better branch-deploy controls and
  file-based routing. The Pages limits page does not announce a deprecation, but
  it points users who need more than 100 sites to Workers static assets. Limits
  are the same on both: 20,000 files (free) or 100,000 (paid), 25 MiB per file,
  `_headers` with at most 100 rules and 2,000 characters per line. Static asset
  requests are free and unlimited on Workers. `_headers` is **not** applied to
  responses generated by Worker code; COOP/COEP for static assets are not
  mentioned on that page **[?]** (test it).
  **Recommendation: one Worker with static assets** (app, API, Durable Object
  bindings in one deploy), not Pages plus Pages Functions. The owner asked for
  Pages; Pages is fine for the static-only demo (Phase 1) and the migration to
  Workers later is documented, but starting on Workers avoids a second move.
* **Rust Workers (`workers-rs`).** Built with `wasm-bindgen`, `worker-build`
  and `wasm-opt`; handlers via the `event` macro or `axum`/`http` feature;
  bindings for Durable Objects (SQLite-backed), KV, R2, D1, Queues, secrets,
  Rate Limiting, Analytics Engine. Caveats from the README: D1 support is
  labelled alpha and queues beta there; "expect a few rough edges"; tokio and
  async-std are unsupported, every dependency must compile to
  `wasm32-unknown-unknown`; default `panic=abort` kills the instance (a
  `--panic-unwind` mode needs nightly and rebuilds `std`); testing is via
  Miniflare with a JavaScript harness. The docs page does not say beta or GA.
  So: Rust Workers are usable but young; plan for papercuts and keep the
  Worker thin.
* **Limits.** Uncompressed Worker size 64 MiB, "no compressed size limit",
  startup 1 s, memory 128 MB per isolate. **CPU per HTTP request: 10 ms on Free,
  30 s default (5 min max) on Paid.** Subrequests 50 (Free) / 10,000 (Paid).
  Workers per account 100 (Free) / 500 (Paid). So the Free plan's 10 ms CPU
  budget rules out anything heavy in the Worker (we do none) and makes P-256
  signature checks a thing to measure **[?]**.
* **Prices.** Workers Paid: $5 minimum per account per month, 10 M requests
  included then $0.30/M, 30 M CPU-ms included then $0.02/M. Free: 100,000
  requests/day.
* **Durable Objects (SQLite).** Free: 100,000 requests/day, 13,000 GB-s/day,
  5 M rows read/day, 100,000 rows written/day, 5 GB stored total. Paid: 1 M
  requests and 400,000 GB-s included per month, then $0.15/M requests and
  $12.50/M GB-s, rows written $1.00/M after 50 M, stored data $0.20/GB-month
  after 5 GB. Incoming WebSocket messages bill 20:1 as requests; outgoing are
  free; duration is billed on wall-clock time while an object is active or idle
  but not eligible to hibernate, at a fixed 128 MB. Limits: 1,000 requests/s per
  object (soft), 2 MB per row/value, 32 MiB per WebSocket message, 10 GB per
  object on Paid.
* **D1.** Free: 5 M rows read/day, 100,000 rows written/day, 5 GB total. Paid:
  25 B reads and 50 M writes per month included, then $0.001/M reads and $1.00/M
  writes, storage $0.75/GB-month after 5 GB. Per-database size limit and
  database count: not on the pricing page **[?]**.
* **R2.** Standard storage $0.015/GB-month; Class A $4.50/M, Class B
  $0.36/M; free each month: 10 GB, 1 M Class A, 10 M Class B; egress free when
  served through R2 APIs or Workers.
* **KV.** Free: 100,000 reads, 1,000 writes/deletes/lists per day, 1 GB. Paid:
  10 M reads, 1 M writes included, then $0.50/M and $5.00/M. Too few writes and
  eventual consistency (the page does not state it; **[K]** it is eventual)
  make it unsuitable for sessions or rate limits. We use it for nothing
  security-relevant.
* **Queues.** Free: 10,000 operations/day, 24 h retention. Paid: 1 M
  operations/month then $0.40/M, retention up to 14 days. Operation = 64 KB.
* **Turnstile.** Free plan: unlimited challenges, 20 widgets, 10 hostnames per
  widget, 7-day analytics, Cloudflare branding remains. Enterprise for more.
* **Email.** Email Routing (inbound) is free. **Email Sending** (outbound
  transactional) is labelled **Beta**, **requires Workers Paid** for arbitrary
  recipients (3,000 emails/month included, then $0.35 per 1,000); sending to
  verified destinations is free. The pages read do not cover daily send limits
  or deliverability guidance **[?]**. Consequence: magic links need the $5 plan
  or a third-party sender.
* **Access / Zero Trust.** The pages read give no seat count or price for the
  free plan **[?]**. Access is for staff (admin dashboard), not for end users.
* **Cloudflare for Platforms** (Workers for Platforms): for running customers'
  code, each as an isolated Worker. Not relevant to a first-party app. It would
  matter only if third-party plugins ran server-side, which this plan does not
  propose.
* **Browser storage.** OPFS: Baseline widely available; `createSyncAccessHandle`
  is for workers only; same quotas as IndexedDB; clearing site data deletes it;
  not user-visible. `showDirectoryPicker()` is "limited availability" and
  experimental; MDN's table was not in what I fetched **[K: Chromium only;
  verify]**. WebAuthn is Baseline since 2019 but the **PRF extension** has
  "varying" support by browser and authenticator **[?]**.

## 3. Architecture

### 3.1 Browser versus edge

Principle: **the browser is the application; the edge is a dumb, encrypted
mailbox.** This mirrors the desktop split (thin UI over a Rust kernel) and
ADR 0013 (relay sees only ciphertext).

```
 Browser (one origin: app.example)
 ┌──────────────────────────────────────────────────────────────┐
 │ Main thread: Svelte 5 UI, CodeMirror. Never runs the kernel. │
 │   ▲ postMessage + transferable ArrayBuffers (zero copy)      │
 │ Kernel Worker (wasm32): manang-kernel + web-capable plugins  │
 │   typst · editor/rope · markdown · writing · search · figure │
 │   diagram · citations · agent (fetch) · live (sans-IO)       │
 │   ─ ProjectFs trait → OPFS (sync access handle)              │
 │   ─ HttpClient trait → fetch                                 │
 │   ─ SyncTransport → WebSocket                                │
 │ Service worker: app shell, wasm, fonts, offline              │
 └───────────────▲──────────────────────────────▲───────────────┘
                 │ HTTPS (cookie session)       │ WSS (ciphertext)
 Cloudflare ─────┴──────────────────────────────┴───────────────
 ┌─────────────────────────────┐   ┌───────────────────────────┐
 │ Worker `manang-web` (Rust)  │   │ Relay Worker (other branch)│
 │  static assets + /api/*     │   │ /room/<id> → DO per room   │
 │  auth, sessions, quotas     │   │ anonymous, no persistence  │
 │  D1: accounts, project index│   └───────────────────────────┘
 │  DO per project: sync log   │
 │  R2: ciphertext blobs       │   Queues: erase, export, mail
 └─────────────────────────────┘
```

**Runs in the browser (Rust to wasm32-unknown-unknown, inside a dedicated
Worker):** the kernel, the editor plugin (rope buffers), Typst compile (the
`typst` crate), Markdown rendering, writing tools, search over the open
project (an in-memory index; no `ignore`/`walkdir`), citations resolution
(fetch behind the existing `HttpClient`-style seam), the figure engine and
diagram rendering (`merman` is pure Rust; check its wasm build **[?]**), the
agent's provider calls (`reqwest` has a fetch backend **[K]**; our crate enables
tokio's `net`, which does not build on wasm, so the feature set must be
gated), and the live-session client (`manang-live` is already sans-IO and
checks on `wasm32`; browser entropy and a WebSocket `SyncTransport` are the
missing parts, ADR 0013 follow-ups).

**Runs on the edge:** authentication and sessions; the project index and
quotas; the per-project encrypted sync log; ciphertext blob storage; the
anonymous live relay; transactional email; erase and export jobs. Nothing
compute-heavy. No Typst, no CRDT decoding, no rendering, no AI proxy by default
(section 3.5).

**Audit first (Phase 0, 2 to 3 days).** Today: `manang-kernel` depends only on
`parking_lot`, `serde`, `toml`, `semver`, `thiserror`: probably fine
**[?: not compiled]**. `manang-buffer`, `manang-editor`, `manang-live`
(documented as wasm32-capable) are good candidates. Known blockers: `manang-project`
(`gix`, `notify`, `ignore`), `manang-citations` (`ureq`),
`manang-agent-providers` (tokio `net`), `manang-typst` and `manang-search`
(`rayon`; on wasm without threads this needs a cfg or a no-op pool **[?]**),
`manang-git` (system `git` subprocess; no equivalent in a browser), keystore
(OS keychain), `manang-wasm-host` (Wasmtime, native only). The audit produces a
table: crate, wasm32 status, blocker, seam to add. The CI job already planned in
phase-2 item 1.2 ("wasm32 check of the web-capable crates") becomes the
guardrail.

**Mapping the invariants.**

* Invariant 1 (thin frontend): holds; the kernel Worker is the Rust engine.
* Invariant 2 (zero-copy IPC): `postMessage` with transferred `ArrayBuffer`s
  replaces `tauri::ipc::Response`; PDFs and SVGs cross as transferred buffers,
  never base64.
* Invariant 3 (threads): Tokio and Rayon do not exist in the browser. The UI
  thread stays free because the kernel is in a Worker. Parallelism needs
  `SharedArrayBuffer`, i.e. cross-origin isolation and `wasm-bindgen-rayon`
  style builds (needs a nightly `build-std` setup **[K]**). **Decision: first
  release is single-threaded in a Worker, no cross-origin isolation.** Measure
  against the 50 ms incremental Typst budget on wasm **[?]**; the budget in
  AGENTS.md 4.2 was set for native.
* Invariant 4 (WASM sandbox for plugins): see section 7.3; third-party plugins
  are not offered on the web in v1.
* Invariant 6 (plain UTF-8 files): see 3.3 and 5.

### 3.2 The frontend reuses what exists

`src/lib/kernel/client.ts` is the `Kernel` abstraction (`kernel.run(commandId,
args)`, events, binary results); it has a Tauri `invoke` path and an in-memory
mock set (`mockTypst.ts`, `mockProject.ts`, `mockMarkdown.ts`, ...) used by
`pnpm dev`. `native.ts` already degrades dialogs for the browser ("a typed path,
a download"). The web build adds a third implementation, `wasmKernel.ts`, that
posts the same `run` calls to the kernel Worker. Mocks become test doubles, not
the product. This is the cheapest path and keeps one UI.

### 3.3 Files, projects and the browser file system

A project is a directory tree of plain files (invariant 6). On the web:

| Storage | Use | Notes |
| :--- | :--- | :--- |
| **OPFS** (default) | The working copy of every web project | Reliable in modern browsers [V: Baseline]; fast sync handles inside the kernel Worker; invisible to the user; cleared with site data; quota like IndexedDB, check `navigator.storage.estimate()`, request `navigator.storage.persist()` **[K]**. Safari may evict script-writable storage after inactivity **[K, verify before promising offline]**. |
| **File System Access** (`showDirectoryPicker`) | "Open a folder on disk", edit in place | Limited availability [V]; treat as progressive enhancement (Chromium). Gives true local-first with your own editor and git beside it. Permission must be re-granted per session **[K]**. |
| **Zip import/export** | Universal path, every browser | Import zip, drag-and-drop folder (`webkitdirectory` upload), export zip. Must be one click and always visible: OPFS is a cache the browser may drop, so the UI shows "last exported" and offers a reminder. |
| **Git** | Not in v1 | No subprocess git in a browser. Pure-Rust `gix` in wasm is unverified **[?]**. Plan: export zip and "download as git bundle" later; push to GitHub via an authorised HTTPS flow is a later phase. |

Design: add `ProjectFs` (read, write, list, stat, remove, rename, watch-less)
as a trait in the project plugin; native implements it with `std::fs` and
`notify`; web implements it over OPFS handles supplied by the Worker host.
Change detection is polling or event-by-our-own-writes in the browser (no
`notify`). This is the largest refactor in the whole plan; its size depends on
how much of `manang-project` calls `std::fs` directly (not measured).

A cloud project (section 5) is the same tree; the cloud copy is ciphertext. The
OPFS or disk copy remains the user-readable form, so invariant 6 holds for
what the user sees; the honest caveat is that a user who only ever used the web
and lost their keys has no plaintext anywhere (section 6.4).

### 3.4 What the web version cannot do

* No system TeX, no `tectonic` native worker, no `latexmk`, no shell escape.
* No local binaries: git subprocess, Biber (AGPL port exists only in the
  Emscripten stacks), external converters.
* No native Wasmtime plugins or native-tier plugins; no OS keychain; no file
  associations; no system fonts (a browser cannot enumerate them without
  `queryLocalFonts` permission **[K]**), so Typst uses bundled fonts only.
* Typst packages (`@preview/...`) need network; the Typst package host's CORS
  policy is unknown to me **[?]**. Plan: a read-through cache Worker for
  package archives (pure forwarding and caching, no user data), plus
  prefetch of a curated list for offline.
* Memory and file size ceilings are the browser tab's, not the machine's; the
  AGENTS.md "idle < 75 MB" budget is a desktop figure. Measure the wasm core's
  idle heap **[?]**.
* No background compile when the tab sleeps; no reliable timers in background
  tabs.

### 3.5 AI agent on the web

Bring your own key remains the model. The key never goes to our servers. Problems:

* Browser calls to a provider need CORS support from that provider. Some
  providers allow browser calls with an explicit opt-in header **[K: Anthropic
  does; verify each provider]**; others do not. Where CORS blocks, the only
  fix is a pass-through proxy that sees prompts and the key in transit. That is
  a privacy exception comparable to ADR 0013's relay, with plaintext instead of
  ciphertext: **default off; if offered, a stateless Worker that logs nothing,
  documented loudly, per-request preview of what is sent (already planned).**
  Owner decision.
* Key storage: the OS keychain does not exist. Options: memory only (re-enter
  every session), or encrypted at rest in IndexedDB under a key from the
  passkey PRF or a passphrase. Any XSS reads it, so the CSP in section 7 is the
  real protection.
* We do not resell AI. No quotas, no payments, no provider contracts.

## 5. Storage and sync design

### 5.1 Where each kind of data lives

| Data | Store | Why |
| :--- | :--- | :--- |
| Accounts, credentials (public keys), sessions, project index, quotas, audit of auth events | **D1** | relational, small, global; reads cheap. Strong consistency across regions: single primary with read replicas **[K]**, verify; sessions can instead live in the account DO |
| Per-project sync: ordered log of encrypted update frames, snapshot pointer, member list | **Durable Object (SQLite), one per project** | single-writer ordering is exactly what a log needs; WebSocket Hibernation gives the live fan-out (the same object serves live and sync); rows capped at 2 MB so chunk frames |
| Large ciphertext blobs: snapshots, images, PDFs, zip exports | **R2**, key = hash of ciphertext | cheap, free egress through Workers; immutable objects are cache friendly |
| Static config, feature flags | **KV** or just code | 1,000 writes/day free, eventual; nothing security-relevant |
| Async jobs: account erase, export build, email retry | **Queues** | 10,000 ops/day on Free; fine at our scale |
| Rate limits | Workers Rate Limiting binding **[?: limits not read]** or a DO counter | KV is the wrong tool |

Why D1 and DO both: D1 answers "what projects does this account have?" with
one query; DO answers "what happened in this project, in order?". A DO per
account holding sessions and index is a valid alternative that removes D1 and
its alpha label in workers-rs; trade: no cross-account queries (admin,
abuse). Start with D1 for the index, decide after the spike (workers-rs D1 is
labelled alpha in its README [V]).

### 5.2 Sync protocol (reuses ADR 0013)

* The unit is the **encrypted envelope** from `manang-live` (XChaCha20-Poly1305,
  AD = version, kind, id), with the **project key** instead of a room secret.
* The server never decodes updates. The DO assigns a monotonically increasing
  `seq`, appends the frame, and broadcasts to connected sockets. A client
  reconnects with `since=<seq>` and gets the missed frames or a snapshot
  pointer. The Worker bundle therefore has **no Loro or yrs**; the engine
  choice (Loro memory growth, ADR 0013) stays a client concern.
* **Compaction** is client-driven: a client uploads an encrypted snapshot to R2
  and tells the DO "snapshot at seq N"; the DO verifies only size, quota and
  that N is not ahead of its log, then drops log rows below N. Because the
  server cannot read content, a malicious member can upload a bad snapshot:
  members are trusted equally (as in ADR 0013); keep the previous snapshot for
  one generation so a bad one can be rolled back.
* **Files, not just one document.** Text files are CRDT documents; binary
  assets are immutable blobs referenced by hash; the project manifest (tree of
  paths) is a small CRDT map. This is new work: ADR 0013 covers one text file
  per session (Beta 1). Multi-file projects and renames are a phase of their
  own.
* **Conflicts.** Concurrent edits to text merge via the CRDT. Binary files:
  last writer wins with the previous version kept (matching the git
  collaboration plan: never text-merge binaries). Offline edits merge on
  reconnect. Divergent "forked" copies (two devices offline for weeks) are
  merged by the CRDT; semantic conflicts are the user's, which the editor shows
  as ordinary text.
* **Limits** (proposals, **[A]**): 100 MB per free project, 25 MiB per file (the
  Workers static asset ceiling is unrelated; R2 allows more, but memory in a tab
  does not), 2 MB per DO row so frames above that are chunked. 32 MiB WebSocket
  message cap [V] sits above the 16 MiB frame cap in ADR 0013.
* **Relation to the anonymous relay.** The relay on the other branch stays
  as is: no accounts, no persistence, a room per invite. Account-backed sync is
  a different Worker route and DO class with persistence and authentication.
  Share the wire envelope and the DO fan-out code, not the deployment.

### 5.3 Offline

A service worker precaches the app shell, wasm modules and fonts under a
versioned cache; the OPFS working copy is the source of truth offline; edits
queue as CRDT updates in OPFS and flush on reconnect. Hazards: a stale wasm
core reading newer data (version every on-disk and on-wire format; refuse to
open data from a newer core with a clear message), service-worker update races
(activate on next load, never mid-session), and storage eviction (section 3.3).

## 6. Accounts and registration

### 6.1 Principle: accounts are optional

The demo and the whole local web workspace work **without an account**. An
account exists to unlock cloud sync, cross-device projects and account-backed
sharing. This keeps the privacy story simple (no account, no data) and makes
abuse protection a Phase 3 problem, not a Phase 1 one.

### 6.2 Sign-in methods

1. **Passkeys (WebAuthn), first.** No passwords, no password database, phishing
   resistant. Discoverable credentials; request user verification. Request only
   ES256 and EdDSA in `pubKeyCredParams` so the server needs two verifiers
   (P-256 ECDSA, Ed25519) from audited RustCrypto crates; attestation "none".
   The `webauthn-rs` crate is the obvious Rust library but I believe it links
   OpenSSL **[K, verify]**, which would not build for a Worker. Hand-written
   assertion verification (parse authenticator data, check rpIdHash, flags,
   signature over authData || SHA-256(clientDataJSON), sign-count policy) is
   about 300 lines but security-critical: it is the first thing for an external
   reviewer.
2. **Email magic link, as the fallback and for recovery.** One-time token
   (256-bit, stored hashed, 10-minute expiry, single use, bound to the
   requesting browser by a cookie so a link opened on another device cannot be
   replayed by someone who read the email). Needs outbound email: Cloudflare
   Email Sending is Beta and Workers Paid only [V]; deliverability guidance was
   not in the pages read **[?]**. Alternative: a transactional provider (cost
   and a third-party processor).
3. **OAuth, optional and later: ORCID (researchers), GitHub, Google.** Plain
   authorization-code flow with PKCE, `state`, exact redirect URIs, and we
   store only the provider's stable subject id and the verified email. ORCID's
   OIDC details are **[?]** (not read). OAuth is for convenience; it never
   becomes the only way in (providers change terms).
4. **No passwords, no SMS, no security questions.**

### 6.3 Sessions, CSRF and abuse protection

* Sessions: a random 256-bit opaque token in a `__Host-` cookie (`Secure`,
  `HttpOnly`, `SameSite=Lax`, `Path=/`, no `Domain`), stored hashed server side
  with created/last-seen/device label, revocable, idle 30 days and absolute 90
  days **[A]**. No JWTs in `localStorage`. WebSocket upgrade checks the cookie
  and the `Origin` header.
* CSRF: same-origin only (app and API on one hostname, no CORS), `SameSite`,
  `Origin` check on every state-changing request, JSON bodies with a required
  custom header; no GET with side effects.
* Re-authentication (a fresh passkey assertion) for: adding or removing a
  credential, changing email, export, delete account, rotating keys.
* **Turnstile** on registration, magic-link requests and recovery requests
  (free: unlimited challenges [V]; branding stays). Per-IP and per-email rate
  limits on those endpoints with hashed keys and short windows. Email-bomb
  protection: one outstanding link per address, cooldowns.
* Abuse of storage: per-account quotas enforced in the DO before accepting
  frames; per-IP caps on anonymous relay rooms (existing: 16 peers, rooms cap).
  Content is ciphertext so we cannot scan it: be explicit in terms and keep a
  takedown path by account or project id (we can delete, not inspect). Owner
  and counsel decision.

### 6.4 What we store and what we never store

Store (account): an opaque user id, email (hashed copy for lookup, plain copy
only if needed to send mail; see decision), credential ids and public keys,
session hashes with coarse device labels, plan and quota counters, timestamps
of creation and last use. Store (projects): ciphertext blobs and log frames,
sizes, member ids, wrapped project keys.

Never store: document plaintext (unless the user explicitly opts into a
"server can read" mode, if the owner chooses to offer one; default off);
passphrases; recovery keys; passkey private keys; AI provider keys; IP
addresses beyond the rate-limit window; analytics tied to a person.

### 6.5 End-to-end encrypted sync: key management in plain words

Goal: the server, and anyone who breaches it, learn nothing about document
content. Cost: the user must hold a way to get their key back.

* Every cloud project has a random 256-bit **project key**. Document frames and
  blobs are encrypted with keys derived from it (HKDF, as in `manang-live`).
* The project key is stored on the server only **wrapped** (encrypted) under
  the member's **account key**. The server stores the wrapped key and cannot
  unwrap it.
* The **account key** is held by the user, never uploaded. Ways to hold it:
  1. **Passkey PRF** [V as an extension; support varies by browser and
     authenticator]: the passkey itself yields a stable secret
     (HKDF -> account key). Best UX: signing in also unlocks. Fails on
     authenticators or browsers without PRF, and the key is tied to that
     credential.
  2. **Recovery key**, shown once at setup: 160 bits or more of randomness as
     grouped words or base32, to print or store in a password manager. Wraps
     the account key a second time. This is the only way back if every
     passkey is lost.
  3. **Passphrase** (Argon2id in wasm, parameters tuned for a phone): for
     magic-link-only users and for browsers without PRF.
* **Plainly: if a user loses every passkey and the recovery key, their cloud
  data cannot be recovered by us, by design.** The app must say so before
  enabling sync, require the user to confirm they saved the recovery key, and
  keep a local plaintext copy on at least the device that created the project
  (so loss of keys is not loss of the document). An opt-in "server-managed
  key" mode would remove this risk and the E2EE claim together; offer it only
  if the owner wants a mainstream convenience tier, and label it truthfully.
* **Sharing.** Anonymous live rooms: the secret in the invite fragment, as in
  ADR 0013. Account-backed sharing: the owner wraps the project key to the
  invitee's public key (a per-account X25519 key published to a directory the
  server holds); the server could substitute keys (a classic E2EE weakness),
  so show a short fingerprint to compare out of band and keep invitee trust on
  first use. Revocation: rotate the project key and re-wrap for remaining
  members; past ciphertext the revoked member already downloaded stays
  readable to them (no forward secrecy; same non-goal as ADR 0013).
* Metadata the server necessarily sees: account email, project ids, sizes,
  times, member graph, IP at the edge (Cloudflare sees it regardless).
* Not built here: key transparency, hardware attestation, multi-device
  approval flows beyond "any signed-in passkey can unlock if PRF works, else
  recovery key or passphrase".

### 6.6 Build in Rust versus a hosted identity provider

| | Own auth in a Rust Worker | Hosted IdP (Clerk, Auth0, WorkOS, Stytch, Supabase, or a self-hosted OSS server) |
| :--- | :--- | :--- |
| Effort | passkeys + magic link + sessions: roughly 3 to 4 weeks one engineer, plus review **[A]** | days to integrate |
| Security risk | ours; auth bugs are the classic breach; needs an external review | theirs, but their breach is also ours |
| E2EE fit | full control of the WebAuthn ceremony, so PRF key wrapping is possible | hosted widgets often wrap the ceremony; PRF exposure unknown **[?]**; E2EE keys would need a separate passphrase/recovery layer |
| Privacy | we hold the minimum | a third party holds emails and login events; needs a DPA; conflicts with "no spying" posture |
| Cost | Worker requests (cents) | per-MAU pricing that I did not verify **[?]** |
| Lock-in and portability | none | migration of credentials is hard |
| Rust-everywhere | yes | the Worker verifies a JWT: small, but a foreign trust anchor |

**Recommendation for a small team:** build a *deliberately small* own auth in
Rust (passkeys, magic link, optional OIDC code flow; no passwords), because the
product's headline property (E2EE with passkey-wrapped keys, minimal data)
depends on controlling the ceremony, and the surface is small once passwords,
SMS and profile management are excluded. Mitigations: freeze scope, use
RustCrypto primitives only, fuzz the authenticator-data and CBOR parsers, write
the threat model before the code, **pay for an external review before Phase 4
(sync) ships**, and keep a documented exit (export, delete). If the team cannot
afford the review or three weeks, the fallback is a hosted IdP for login only,
with E2EE keys held by a passphrase and recovery key independent of the IdP,
and PRF treated as a later upgrade. Owner decision D3.

### 6.7 GDPR basics

* Role: we are the controller for account data; for ciphertext we are a
  processor-like host of data we cannot read (counsel to confirm).
* Lawful basis: contract for the account; consent for any optional
  analytics; none needed for strictly necessary cookies (the session cookie).
* Export: account JSON (profile, credentials list, sessions, projects index) and
  per-project zip built client side (we cannot decrypt server side). Erase:
  delete account and cascade through a queue to D1 rows, DO storage and R2
  objects, verified by a job and logged without content; target within a
  stated number of days **[A: 30]**; confirm backups behaviour (D1 Time Travel
  retention **[K, verify]**).
* Location: Durable Objects and R2 offer jurisdiction restrictions such as EU
  **[K, verify exact names and plan limits]**; D1 location hints **[K]**. State
  plainly that Cloudflare's edge network handles traffic globally.
* DPA with Cloudflare and with any email provider; a sub-processor list; an
  honest privacy page. No tracking, no third-party scripts, no fonts from
  third-party hosts (self-host DM Sans / DM Mono; the Fundaments design system
  is already self-contained).
* Children: say 16+ (or the local age), no marketing profiling anyway.

## 7. Security and privacy review

### 7.1 Threat model (summary)

Assets: user documents, the account key and project keys, AI provider keys, the
session, the availability of the service. Adversaries: (a) a network attacker
(TLS, HSTS); (b) a malicious website or XSS in our origin (the worst case: it
reads OPFS, memory, the PRF-derived key, the BYO API key); (c) a malicious
project (a Typst or Markdown file that tries to run code or exfiltrate; Typst
has no network or file access beyond the project and packages; Markdown
rendering must sanitise HTML and SVG); (d) a malicious collaborator holding the
room/project key; (e) a curious or breached server operator (E2EE addresses it
for content, not for metadata); (f) a compromised dependency or CDN; (g) abusive
users (spam, storage, relay flooding); (h) account takeover through email.

### 7.2 Browser hardening

* **CSP** (via `_headers` for assets; the Worker sets headers on API/HTML it
  generates, since `_headers` does not apply to Worker responses [V]):
  `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self';
  img-src 'self' blob: data:; font-src 'self'; connect-src 'self' wss://<relay>
  https://<chosen providers>; worker-src 'self' blob:; frame-src <plugin
  origin>; object-src 'none'; base-uri 'none'; form-action 'self';
  frame-ancestors 'none'`, plus Trusted Types for the few `innerHTML` sinks.
  The need for `'wasm-unsafe-eval'` to compile wasm is **[K]**; confirm. No
  inline scripts, no `eval`. `connect-src` is the exfiltration fence for the AI
  agent: a user-supplied provider URL is a user decision and should be an
  explicit setting.
* `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: no-referrer`, `Permissions-Policy` denying camera, mic,
  geolocation; `Cross-Origin-Opener-Policy: same-origin`. The `_headers` limits
  are 100 rules and 2,000 characters per line [V].
* **Cross-origin isolation** (COOP `same-origin` + COEP `require-corp` or
  `credentialless`) is required for `SharedArrayBuffer`. Costs: every
  cross-origin subresource needs CORP/CORS, OAuth popups using `window.opener`
  break (use redirect flows), embedding is harder. Plan: **do not require it
  in v1**; add it only if the single-thread Typst measurement fails the budget.
* **Supply chain:** `cargo deny` and `cargo vet` or audits on the wasm
  dependency set, `pnpm` lockfile with `--frozen-lockfile`, pinned CDN-free
  assets (no third-party scripts at runtime, everything self-hosted, with SRI
  for the precached shell), reproducible wasm builds where practical,
  signed release tags, GitHub Actions pinned by commit hash, minimal CI
  secrets, a separate Cloudflare API token per environment with least scope.
  Fonts and wasm engines for LaTeX later come from our own bucket, hash-pinned
  (research decision 2).

### 7.3 Third-party plugins in the browser

Desktop plugins are Wasmtime components with capability imports (ADR 0003). A
browser does not run Wasmtime or the component model natively; options are to
transpile components to core wasm plus JS glue (for example the Bytecode
Alliance `jco` **[K, maturity unverified]**) or to define a smaller core-wasm
ABI for the web. **Web v1 ships first-party plugins only**, compiled in. A
future web plugin tier needs its own ADR and these rules: plugin logic in a
dedicated Worker with `Memory` `maximum` set, no ambient `fetch` (the host
passes capability functions), termination of the Worker as the timeout (no
epoch interruption in browsers), manifest consent as on the desktop, and plugin
UI in a sandboxed `<iframe sandbox="allow-scripts">` served from a **separate
origin** (for example a distinct registrable domain) so even a sandbox escape
does not share storage with the app, communicating only through the versioned
`postMessage` bridge from platform-v2 3.4. Server-side execution of plugins is
out of scope (and is where Workers for Platforms would apply).

### 7.4 Residual risks stated plainly

XSS is the single point of failure for local keys; the server can still lie
about key directories (mitigated by fingerprints); metadata is visible;
Cloudflare is a trusted third party for availability and metadata; recovery of
E2EE data is impossible without a recovery key; WebAuthn PRF is not universal;
Rust Workers are young.

## 8. Rust everywhere: build, test, observe, cost

### 8.1 What is Rust

* **Browser:** the kernel Worker (wasm32), built with `wasm-bindgen`/`wasm-pack`
  style tooling and optimised with `wasm-opt`; the thin glue to the Svelte UI is
  TypeScript (types generated from the manifests where possible).
* **Edge:** a Worker `crates/manang-web` built with `workers-rs`
  (`worker-build`): auth routes, sessions, project index, quotas, DO classes
  (project sync log, account state), Queue consumers. Shared crates:
  `manang-live` envelope and protocol types (so client and server agree on
  framing, and the server uses only the unauthenticated header parts);
  a small `manang-web-proto` for API types, `serde`-shared with the client.
* **Not Rust:** the Svelte UI; the relay Worker on the other branch (TypeScript,
  about 80 lines per ADR 0013); the service worker (JavaScript).

Wasm size and startup: the Worker limit is 64 MiB uncompressed [V], with a 1 s
startup limit; a thin auth/sync Worker with `panic=abort`, LTO and `wasm-opt`
should be small but I have no measurement **[?]**; the browser kernel wasm
(Typst plus fonts) will be tens of MB; budget and lazy-load it (fonts as
separate hashed files, Typst wasm cached by the service worker). A static asset
may be at most 25 MiB [V], so large fonts or wasm must be split.

### 8.2 Pipeline

1. `cargo check --target wasm32-unknown-unknown -p <web-capable crates>` in CI
   (already planned), then `wasm-pack`/`wasm-bindgen` build for the kernel
   Worker; `worker-build --release` for `manang-web`.
2. `wrangler.toml` (or `wrangler.jsonc`) with environments `dev`, `staging`,
   `prod`; bindings for D1, DO classes with migrations, R2, Queues; secrets via
   `wrangler secret`.
3. Frontend: `pnpm build`; static output into the Worker's assets directory;
   `_headers` generated from one source of truth.
4. Deploy: GitHub Actions on tag, `wrangler deploy` with a scoped API token;
   preview deploys per branch for the owner to try (Workers versions/preview
   URLs **[K]**).
5. Gates per AGENTS.md section 5 apply; add a size budget check for both wasm
   artefacts and a Lighthouse/Web Vitals budget (cold load on the web has no
   equivalent of the 400 ms native launch budget; define a web budget, owner
   decision).
6. AGENTS.md 7.4 (no statically bundled C system libraries) is easier on the
   web: nothing links against the system; still, `cargo tree` bans stay.

### 8.3 Testing locally

* Unit and property tests run natively (`cargo test`) for logic crates; add a
  `wasm-bindgen-test`/headless Chromium job for the browser glue (OPFS,
  WebSocket transport).
* Worker: `wrangler dev` runs `workerd` locally with local D1, DO and R2
  simulators; `workers-rs` documents Miniflare-based tests with a JS harness
  [V]. Run the local relay `manang-relay` binary for the client against a
  second implementation of the same wire contract.
* Playwright (already in the pyramid) drives the web build against local
  `wrangler dev`: sign-in with a virtual authenticator (Chromium CDP WebAuthn
  emulation **[K]**), sync between two browser contexts, offline toggling,
  quota exhaustion.
* Fuzz targets (60 s cap per AGENTS.md): CBOR/authenticator-data parsing,
  envelope header parsing, API request decoding.
* Do not run `wrangler dev`, Playwright and a workspace Rust build at once
  (AGENTS.md 7.3 concurrency budget).

### 8.4 Observability without spying

* Server: Workers Logs / tail for errors with request ids; **Analytics Engine**
  (a workers-rs binding [V]) for aggregate counters only (requests by route and
  status class, sync frame counts, quota rejections); never a user id or IP in
  a metric; logs scrub tokens, emails and project ids (or hash them with a
  rotating salt); short retention.
* Client: no analytics by default; opt-in crash reports with stack trace and
  build id only, shown to the user before sending (same stance as the desktop
  plan); a "copy diagnostics" button for support.
* Status and health: `/health`, a public status page, alerts to the owner on
  error rate, DO overload errors (1,000 req/s soft limit [V]) and spend.
* Be explicit: Cloudflare itself sees IP addresses and request metadata as the
  edge operator.

### 8.5 Cost model

Assumptions (**[A]**, change them and recompute): per monthly active user
(MAU) 2,000 API requests (auth, project list, batched sync); static asset
requests are free [V]; average 5 ms CPU per API request; 10% of MAU host 2
live sessions a month, each 2 people for 2 hours with an always-chatty room
(ADR 0013's sizing: 3,600 billed requests per session; and, which ADR 0013 did
not count, **duration**: a room receiving a message every 100 ms never
hibernates, so 2 h x 128 MB = about 920 GB-s per session); 30% of MAU use cloud
sync with 25 MB of ciphertext each; 1.5 emails per MAU a month; DO log storage
5 MB per synced project. Prices from section 2.

| | 100 MAU | 1,000 MAU | 10,000 MAU |
| :--- | :--- | :--- | :--- |
| API requests (per month) | 0.2 M | 2 M | 20 M |
| Live sessions | 20 | 200 | 2,000 |
| Live DO duration | 18 kGB-s | 184 kGB-s | 1.84 MGB-s |
| R2 stored | 0.75 GB | 7.5 GB | 75 GB |
| Emails | 150 | 1,500 | 15,000 |
| Plan | Free works for everything except magic-link mail (needs Paid) | Paid ($5): everything under included amounts | Paid |
| Estimated bill | $0 to $5 | about $5 | about $30 to $45 |

How the 10,000 figure is built: $5 base; requests 10 M over x $0.30 = $3; CPU
(20 M x 5 ms = 100 M ms, 70 M over x $0.02) = $1.40; DO requests 7.2 M, 6.2 M
over x $0.15 = about $0.90; DO duration 1.44 MGB-s over x $12.50 = about $18;
R2 65 GB over x $0.015 = about $1; DO storage 10 GB over x $0.20 = $2; email
12,000 over x $0.35/1,000 = $4.20. Sum about $35; the range reflects the
assumptions. On the **Free plan** the live duration cap is 13,000 GB-s/day, about
14 two-hour chatty sessions a day [V + computed].

What this says: money is not the constraint; **duration of active live rooms**
is the only line that grows meaningfully, which argues for batching presence
and keystroke frames (fewer wake-ups, more hibernation) and for the self-hosted
relay remaining an option. It excludes: domain, the owner's time, the external
security review, support, legal, any email provider alternative, and
Cloudflare features I did not price (Rate Limiting binding, Images, Browser
Rendering: not needed). It assumes no abuse; a flood of anonymous rooms or
storage is the real cost risk, hence quotas and Turnstile.
