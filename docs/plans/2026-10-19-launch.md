# Launch plan: open source, releases, hosting, docs

Owner decisions of 2026-10-19: Manang is open source under the MIT licence, like Theorem and Lemma; installers and the LaTeX engine ship through GitHub Releases; **live collaboration is invite-only** (a session is joined with an invite link; nothing is public); everything is connected and deployed from the repositories. The DeepSeek agent test passed.

## 1. The map: what lives where

| Piece | Where it lives | Hosted at | Deployed by |
| --- | --- | --- | --- |
| App, crates, relay Worker, registry tooling, docs sources | `Fundaments-Work/Manang` (public, MIT) | GitHub | git push |
| Installers (AppImage, deb, rpm, msi/exe, dmg), updater manifest, LaTeX engine binaries | GitHub Releases of `Manang` | `github.com/Fundaments-Work/Manang/releases` | tag push (release workflow) |
| Landing page | `Fundaments-Work/manang-landing` (public) | Cloudflare Pages, `manang.fundaments.work` | Cloudflare Git builds |
| Docs site (Starlight) | `Fundaments-Work/fundaments-landing` (`/docs`), content synced from each product repo | `fundaments.work/docs` | Cloudflare Git builds |
| Plugin directory (web) | built from the signed `index.json` at site build time | `manang.fundaments.work/plugins` | Cloudflare build hook after a registry publish |
| Live-editing relay | `Manang/relay/worker` | Cloudflare Worker, `relay.manang.fundaments.work` (workers.dev as fallback) | `wrangler deploy` |
| Plugin registry (signed index, mirrored artifacts) | `Manang/registry` | Cloudflare Worker + R2, `registry.manang.fundaments.work` | `wrangler deploy` + upload |
| Shared facts (support links) | `Fundaments-Work/content` | consumed by the sites | sync scripts |
| Design system | `Fundaments-Work/design-system` | consumed by the sites and the app | manual |

Defaults the app embeds at build time: `MANANG_REGISTRY_URL` (registry host), `MANANG_ENGINE_BASE_URL` (`https://github.com/Fundaments-Work/Manang/releases/download`, so an engine file is `<base>/tectonic-0.17.0/<file>`, a release tagged `tectonic-0.17.0`), the updater endpoint (`.../releases/latest/download/latest.json`), the default relay address (decision below).

## 2. Opening the source

Order matters: a public repo gets unlimited Actions minutes and free CodeQL, secret scanning and dependency review, so open it **before** the release builds.

1. **History.** The pack is 225 MB because an early commit carried build output (`echo-guest/target`), and the test suite has fake keys on purpose (redaction fixtures, AWS's documented example). Rewrite on a fresh clone with `git filter-repo` (drop that path, keep the author as is), run gitleaks over the result, and force-push to the private repo while it is still private. Nothing public is rewritten.
2. **Licences.** MIT for our code (`LICENSE`, done). Ship a third-party licence report with every installer (`cargo about` for Rust, `license-checker` for npm) because the engine and some dependencies are GPL/LGPL/OFL; the installer's About page lists them.
3. **Repository settings.** Public; enable Discussions, private vulnerability reporting, secret scanning with push protection, Dependabot alerts; branch protection on `main` (PRs, the quick CI job required, no force pushes); labels (`good first issue`, `help wanted`, `plugin`, `security`); issue forms and the PR template exist already; `CODEOWNERS` exists.
4. **README and docs for strangers.** Remove "private beta, invite only" for the code (the *app* beta is public now; collaboration is invite-only), add install instructions per OS, a contributor quick start, and the architecture map. Keep `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md` (add a conduct contact).
5. **Flip to public**, set the topics and the social preview image, announce.

## 3. Releases through GitHub

* **Tags.** `v0.1.0-beta.1` style tags build a pre-release; `v0.1.0` builds a release. `engine-v*` / `tectonic-<ver>` tags publish the LaTeX engine files.
* **Release workflow** (`release.yml`, tag-triggered, matrix on `ubuntu-24.04`, `windows-latest`, `macos-latest`): `pnpm install`, `tauri build` with `tauri-apps/tauri-action`, artifacts: AppImage, `.deb`, `.rpm`; NSIS `.exe` and `.msi`; a universal `.dmg`. SHA-256 sums and the third-party licence report attach to the release. The workflow sets `MANANG_CHANNEL=beta` for pre-releases and the embedded URLs above.
* **Updates.** The Tauri updater with its own ed25519 key (a repo secret, backed up offline) reads `latest.json` from the release; a `beta` and a `stable` channel are two manifests (`latest.json` on stable releases, `beta.json` on pre-releases). Updates are signed even though the installers are not OS-signed.
* **Signing.** Start unsigned: Windows shows SmartScreen ("More info, Run anyway") and macOS needs "Open Anyway" (Gatekeeper); the install page explains both with screenshots. Linux needs nothing. Apple notarisation ($99/year) and a Windows certificate or Azure Trusted Signing can be added later without changing anything else.
* **Engine.** `release-engine.yml` builds the static Linux worker (then Windows and macOS) and attaches it to the `tectonic-0.17.0` release; the manifest in `engines/manifest.json` gets its hashes from that run.
* **Cadence.** Beta tags as needed (weekly at most); every tag runs the full CI first (free once public).

## 4. Live collaboration: invite-only by design

A session is a random 128-bit room id plus an end-to-end key that lives only in the invite link's fragment; the relay sees ciphertext and cannot be joined without the link. That is the invite-only model, so no accounts are needed. Hardening to add: relay limits per client (exists), an optional relay allow-list for organisations (the setting `live.relay-url` already points a lab at its own relay, and the Rust relay binary is the self-host option), and a setting to turn live editing off (policy key `collab.live`).

## 5. Connecting everything

* The landing page links to the latest release (download buttons by OS, detected client-side, with the unsigned-installer notes), the docs, the plugin directory and Discussions.
* The app's Help menu opens the docs site; "Send feedback" explains Discussions and issues; About shows the version, commit and channel (done).
* The docs site pulls `docs/user`, `docs/plugins*.md` and generated reference pages from `Manang` at a pinned commit (`sync:docs`), with "Edit this page" links to the repo.
* The plugin directory page and the in-app Browse read the same signed index. A merged registry entry triggers the index build workflow, which uploads the index and artifacts to R2; the web directory rebuilds through a Cloudflare build hook.
* One changelog (`CHANGELOG.md`) feeds the release notes, the landing page and the in-app "What's new".

## 6. Documentation plan

User guide (exists, 18 pages), plugin authoring (exists) plus publishing (exists), generated references (commands, settings, shortcuts, agent tools, file formats, WIT interfaces: a script reads manifests and registries and writes Markdown), contributor guide (architecture, crate map, testing pyramid, release process), ADRs (exist, 16), operations (relay, registry, engine, release). Theorem and Lemma get their user docs written before they join the docs site.

## 7. CI after the repo is public

Minutes stop being a budget, so: the full tier on every push to `main` (clippy, all tests, wasm32, cargo-deny, UI suite), the quick tier on pull requests, CodeQL and dependency review on, nightly macOS and Windows test jobs, Dependabot weekly. Keep the cache-key discipline.
