(`rig-core`/`rig-http`/`rig-reqwest` pinned `=0.44.0`). No real API calls, no keys: everything

## Verdict: PASS, with documented small differences

Rig is usable below our loop. Assistant history replays byte-exact (signatures, `redacted_thinking`,
tool_use), streaming maps event for event onto our `ProviderEvent`s, cancellation, retry, offline
and redaction plug in. The differences are request-shape differences (all API-equivalent) plus a
few Rig-added request fields. Proceed with the migration as "hybrid i"; the adapter ships in
`manang-agent-rig` (Part 2 done), in-house adapters untouched as the exit plan.

### A. Anthropic request body, in-house vs Rig (same conversation)

1. Top-level key order differs (`model, messages, max_tokens, system, tools, [cache_control,] thinking, stream, tool_choice` vs ours `model, max_tokens, stream, system, messages, tools`). Deterministic.
2. `system`: array of text blocks vs our plain string when no cache marker.
3. `tool_result.content`: `[{"type":"text","text":"ok"}]` vs `"ok"`; `is_error` omitted when false.
4. Rig adds `thinking: {"type":"adaptive","block_binding":{"prefix_mismatch_behavior":"drop_block"}}` and header `anthropic-beta: thinking-binding-controls-2026-08-01` for models its catalog marks as context-binding (claude-sonnet-5-5 is). We never sent `thinking`. Cannot be removed through options.
5. Rig adds `tool_choice: {"type":"auto"}` whenever tools exist (we never send `tool_choice`; `auto` is the default, so equivalent).
6. `eager_input_streaming: true` on tools: Rig default; the adapter turns it off by default (setting `eager_tool_input`).
7. Cache markers: with Tools+System+Message(last) breakpoints the markers land on the identical blocks (system, last tool, last block of last message). Arbitrary `Message(i)` breakpoints cannot be placed (Rig places by rule); the adapter treats any breakpoint as "use Rig's three".
8. Everything else identical: `max_tokens`, model, tool definitions, thinking `signature`, `redacted_thinking`, text, tool_use blocks. Unsigned thinking from another provider is dropped by the adapter, as before (Rig would send it as text).

Items 4 and 5 are the only extra *fields*; if byte parity ever matters, the `RequestTap` can strip them (it can rewrite the body). The audit log then records what is actually sent.

### B. DeepSeek request body

- `system`: array of text blocks vs string; `stream`/`tools`/`max_tokens` order differs.
- Assistant message: no `"content": ""` when there is only reasoning + tool_calls; `reasoning_content` present. Messages without reasoning get `reasoning_content: ""` (Rig sends the field on every assistant message, as DeepSeek requires).
- `tool_calls[].function.arguments` and tool message identical. Key order inside `tool_calls` differs (`type` before `id`).

## What had to be done in the adapter (not in Rig)

- History blocks carry the raw provider item as `native` plus an `Origin` (api, provider, model) so Rig replays them verbatim. Without an `Origin` Rig turns reasoning into plain text (first run showed `reasoning_content: ""` and the thinking in `content`). For DeepSeek the reasoning needs a native `{"reasoning_content": text}` item.
- Usage: Anthropic `input` = Rig `input_tokens` minus cache read and write.
- `Started.model` is the requested model: Rig fills the provider-reported model only when the reply ends. (In-house gave the reported one; the two are equal in every cassette.)
- Request-id header for DeepSeek set on the dialect copy (`x-request-id`); error request id prefers the response header over the body.
- DeepSeek-style streams: Rig ends a reasoning part after the text part that follows it; blocks are re-sorted into message order at the end, as in-house.
- `max_completion_tokens` for non-OpenAI gateways cannot be forced (Rig scopes it to OpenAI reasoning models). Custom key header: only `api-key` supported. Raw image/document user blocks are not forwarded.

## Dependency facts

- `cargo tree -p manang-agent-rig | grep -iE "aws-lc|openssl|native-tls|harfbuzz|freetype|icu4c|-sys"` prints only `openssl-probe` (pure Rust, CA directory probing, comes with rustls platform verifier, same as the in-house crate) and `linux-raw-sys` (pure Rust syscalls). No C library crates. 386 tree lines.
- Rig's own `reqwest` feature is not needed: we pass `ReqwestClient::from(our_client)`; `rig-core` is built with `default-features = false` and no features.
- Rig needs rustc 1.95; the workspace MSRV is now 1.95, so no change.
- `rig-core` turns on `serde_json/preserve_order`; the workspace already does.

## Risks

- Churn: a release every 2-3 weeks with breaking changes; pinned `=0.44.0`, all Rig types private to this crate, the cassette/replay tests are the upgrade gate.
- Behaviour we do not control: extra request fields (A4, A5), catalog-driven decisions (`binds_context`, forced tool choice rules), Rig adding fields in the future. Mitigation: audit through `RequestTap`; golden tests.
- Rig's `Origin` model means history stays tied to provider+model: switching model mid-conversation makes Rig downgrade foreign thinking to text (Anthropic) unless filtered; the adapter filters unsigned thinking.
- Retry sits below the tap: audit shows one entry per logical request.
- Part of the real value (provider API tracking, 20+ providers) is untested here against live APIs; live tests remain ignored/manual.
